# Architecture Documentation

Phases 1-4 of applying the "Architecture Documentation Generation" methodology
to crustly (see the analysis in the session that created this - a full
multi-tool pipeline would be overkill for a single-crate CLI project already
served by [graphify](../graph/README.md); this directory covers the
high-value slice: crate/dependency facts, C4-style diagrams, advisory
validation reports, an editor symbol index, and ADRs).

## Phase 1 - crate facts and C4 diagrams

- `repository.md` - generated from `Cargo.toml` + `cargo metadata` by
  `scripts/generate-architecture-docs.sh`. Re-run the script after changing
  dependencies or bumping the version; do not hand-edit.
- `context.md` - C4 System Context (L1), hand-authored, Mermaid.
- `containers.md` - C4 Containers (L2), hand-authored, Mermaid, mirrors
  `docs/ARCHITECTURE.md` §1.

## Phase 2 - validation (unused deps, import cycles, orphan modules)

- `VALIDATION.md` - generated by `scripts/validate-architecture.sh`. Runs
  `cargo machete` (unused dependencies) and analyzes `docs/graph/graph.json`
  for file-level import cycles and orphan modules. Every finding is
  cross-checked with a whole-repo grep before being called real, since both
  cargo-machete (static text matching) and graphify's tree-sitter extraction
  (misses some import styles, e.g. `use super::x`) produce false positives on
  their own. Advisory only - never fails a build; re-run by hand or in CI.

## Phase 3 - module coupling vs graphify communities

- `module-coupling.md` + `dependency.dot` - generated by
  `scripts/analyze-module-coupling.sh`. Uses `cargo modules dependencies`
  (rust-analyzer-verified, ground truth) to build the real module dependency
  graph, cross-referenced against graphify's community detection for
  directory cohesion, and checked against `containers.md`'s declared
  one-directional layering. This run found a real layering inversion: `db`,
  `llm`, and `services` all depend on `tui::plan` for the Plan domain model
  (`PlanDocument`, `PlanTask`, ...), which physically lives in the UI layer -
  see the report for the fix. Render `dependency.dot` with any Graphviz
  viewer, or `dot -Tsvg dependency.dot -o dependency.svg` if graphviz is
  installed locally (not assumed to be present in every environment).

## Phase 4 - editor symbol index, ADRs, and doc-drift check

- `scripts/generate-ctags.sh` - generates a Universal Ctags `tags` file at the
  repo root for editors (vim, emacs, etc). Not committed (gitignored) -
  regenerate on demand; it's a local convenience index, not something worth
  diffing.
- `decisions/` - Architecture Decision Records, the one thing in this
  directory that's deliberately hand-written, not generated (a generator
  cannot know *why* a decision was made). Seeded with the meta-ADR plus three
  backfilled from real decisions already described in `docs/guides/` and
  `docs/development/`: sqlx over rusqlite, Crabrace replacing Catwalk, and
  Plan Mode's read-only/approval-gated design (which documents the layering
  inversion Phase 3 found as a tracked consequence). See `decisions/README.md`
  for when and how to add one.
- `DRIFT.md` - generated by `scripts/check-architecture-drift.sh`. Cross-
  checks `docs/ARCHITECTURE.md` §3's named "Core Components" against the
  current graph (flagging anything documented that no longer has a matching
  node - renamed or removed), and the graph's current top god nodes against
  `ARCHITECTURE.md`'s prose (flagging load-bearing abstractions nobody wrote
  up). Substring-based name matching, so every flag is a lead, not a verdict.

## What this is not

- No Component (L3) diagrams beyond what `module-coupling.md`'s directory
  breakdown gives you.
- No Structurizr/LikeC4, Neo4j/Memgraph, Gephi, or PlantUML/D2 - graphify's
  own `graph.json` + CLI (`query`/`path`/`explain`) already cover graph
  exploration at this project's scale; adding a second graph database or a
  parallel architecture-as-code DSL would just be two things to keep in sync
  instead of one.
- `docs/ARCHITECTURE.md` remains the detailed narrative; `containers.md` is
  its GitHub-renderable summary, not a replacement.
- No rust-analyzer batch indexing beyond what `cargo modules` already uses
  internally in Phase 3 - a standalone semantic-index pipeline is an LSP
  concern, not a docs-generation step (see the original plan's rationale).
- None of Phase 2/3/4's scripts are wired into git hooks or CI - unlike the
  Rust-only knowledge-graph rebuild (fast, free), `cargo machete`/`cargo
  modules`/ctags are slower or need human judgement on their findings, so
  they're run by hand for now.

See [`docs/graph/README.md`](../graph/README.md) for the AI-facing knowledge
graph and its automation, which already covers most of what the guide calls
the "Symbol Graph" / "AI Documents" layers.
